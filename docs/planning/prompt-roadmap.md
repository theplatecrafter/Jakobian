# Per-prompt development checkpoints

The owner requested this workflow on 26 October 2026. Each `continue development` advances the next checkpoint after the current one is accepted. `redo development` retries the current checkpoint, preserving its original acceptance criteria and evidence; it does not advance the queue. A retry records what failed, the repair and the new assessment. If a dependency changes a future checkpoint, explain and revise that future checkpoint before starting it. Do not quietly reduce a current checkpoint's criteria to obtain a pass.

At the start, state one bounded goal and its acceptance criteria. At the end, retain build/test evidence, reflect on the outcome, request an independent review scored out of 100, and report the grade plus material limitations. An independent grade is an engineering assessment, not proof that the full framework is finished. The owner makes the final continue/redo decision. A failed or incomplete checkpoint remains current.

## P01 — general-solid surface context (completed, development 0.7.0)

Goal fixed before implementation: expose a gravity-aware local query and an explicitly supplied rigid-frame Unity bridge for sphere/torus geometry. This is the missing semantic layer between the existing closed-solid queries and a later KSP general-body runtime. Existing radial gameplay remains supported.

Acceptance criteria:

1. One coherent analytic provider supplies closed-solid classification, nearest surface and bounded ray queries. The context distinguishes signed nearest distance, reference-sphere datum altitude and first boundary contact along supplied gravity. Each optional result has explicit availability; an absent ground result never becomes a numeric zero altitude.
2. Gravity defines navigation up independently of geometry. Zero gravity, undefined heading, ambiguous nearest points, solid interiors, boundary starts, misses, tangencies, invalid inputs and exhausted geometry budgets have documented outcomes. Failed/budget-limited casts must not publish a partial contact as usable ground.
3. Sphere and torus checks use independently known distances/orientations. Cover outer/inner/top surfaces, a ray through the empty hole, an inner-wall case where nearest surface and gravity-down contact differ, and deterministic randomized samples. The Unity bridge must preserve metre distances, gravity and normals under translation/rotation, reject invalid/scaled frames, and match native collider contacts in a graphics-enabled KSP run.
4. Release builds without warnings/errors, core checks pass, the baseline receives the exact tested binaries, native startup/context checks pass and the existing Atlas flight/contact/save/reload path passes. Existing fixture configuration/assets and retained save inputs are unchanged. Preserve original/player saves; retain an updated human-testing entry and exact evidence.
5. Document the public experimental API, executed evidence and remaining work. This increment does not promise a playable torus, KSP cache injection, vessel anchors, centrifuge physics, new gravity fields or environments. Code paths that alter existing flight behavior are outside this checkpoint.

Assessment rubric (100 points): contract/edge-case correctness 30; independent tests/native evidence 30; regression safety/deployment 20; authoring/API/evidence documentation 15; scope honesty 5. Acceptance target: at least 85, all five criteria met, and no unresolved major defect. A correctness defect that can publish false usable ground or silently mis-transform a frame caps the grade at 59 until repaired. The reviewer must cite concrete evidence, deductions and untested limits, and must not edit implementation files.

Status: **completed and accepted by the owner's next continue prompt**. Development 0.7.0 met criteria 1–5 and received an independent **96/100**. ## P02 — saved-world descriptor reconciliation (completed, development 0.8.0)

Persist versioned, deterministic identities for supported bodies and their geometry/terrain/dynamics inputs. Test exact reload, changed geometry/assets/provider/index, missing bodies, additive bodies, unsupported schemas and legacy saves. Retain unknown data and original saves. Benchmark: a native private save roundtrip and mutation fixtures produce explicit reconciliation results; unsafe changes cannot be silently adopted as compatible. Define the admission/legacy policy before implementation and distinguish diagnostics from actual load blocking.

Policy fixed before implementation: this increment records and reconciles the implemented Jakobian radial worlds, not arbitrary third-party/stock world geometry. KSP's inspected `Game.Load` calls the load event after `FlightState.Load`; ordinary scenario/event callbacks cannot be advertised as pre-physics admission barriers. P02 therefore installs **persistent compatibility diagnostics and immutable saved baselines, not a universal game-load blocker**. A mismatch must remain incompatible and retain its original descriptors through save/reload. Later general-body admission must consume these results before enabling unsupported visits; that enforcement remains a separate gate.

Unrecorded games (including legacy saves) are **unverified**. Explicitly recording the current baseline establishes a comparison point from that moment, not proof that historical geometry was unchanged. New/additive bodies may be recorded only when every previously recorded body still matches. Missing providers/bodies, changed native identity/index, assets, geometry or dynamics cannot be silently replaced with current values. Unknown/malformed/future records are retained and diagnosed, never automatically downgraded.

Acceptance criteria, fixed before coding:

1. Deterministic, culture-independent, versioned descriptors cover stable/native identity, current provider/generator, effective shape/terrain/maps/biomes, gravity/rotation and orbit/parent inputs. Same semantic inputs are independent of source ordering; byte changes in referenced maps are detectable. Constructors and catalogs reject duplicate/invalid identities and enforce bounded records.
2. Reconciliation distinguishes exact compatibility, safe additions, unverified legacy, missing/changed bodies, invalid records and unsupported versions. Changes to geometry/assets/provider/native index/dynamics are incompatible; saved records are immutable. Unsupported/unknown data survives semantic ConfigNode roundtrip. Neither failed parsing nor re-saving an incompatible snapshot may adopt current definitions.
3. A per-game native scenario stores the descriptor baseline, provides visible diagnostics and explicit first-adoption action, and survives real private-game save/reload. State does not leak between game instances. Supported metadata/extensions are preserved; future/invalid records remain preserved and non-compatible. Diagnostic behavior and the absence of pre-physics load blocking are explicit in the player/API documentation.
4. Independent core mutation fixtures and native ConfigNode/disk fixtures exercise the policies above, including skipped/missing baselines, unsupported schemas, duplicate/tampered records and repeated roundtrip. The existing Atlas landing/navigation/contact/save/reload passes with the scenario present and its adopted descriptors restored. Zero-warning Release build, exact tested baseline deployment, unchanged fixture/assets/template DLLs and preserved preexisting/original saves are recorded.
5. Retain exact evidence, human-testing guidance and an honest reflection, then an independent assessment. No playable torus, migration engine, native vessel anchors or unsafe-game admission guarantee is credited to P02.

Rubric: descriptor/reconciliation correctness 30; core/native evidence 30; regression/deployment/preservation 20; documentation/policy 15; scope honesty 5. Target at least 85, all criteria met, no unresolved major defect. Silent adoption of incompatible/future data or cross-game baseline leakage caps the grade at 59 until repaired.

Status: **completed and accepted by the owner's next continue prompt**. Development 0.8.0 met criteria 1–5 and received an independent **96/100**. ## P03 — detached general-body construction and scaled preview (completed, development 0.9.0)

Use the general geometry/query contracts to create an experimental torus descriptor with stable identity and a hole-preserving scaled representation. Benchmark: an explicitly launched native fixture publishes and binds the torus once, retains stock/radial bodies, validates dimensions and map/scene lifecycle, and passes P02 reconciliation. Declare flight/contact access unsupported until its admission and spherical-consumer adapters are tested. Decide whether a visible human preview can safely ship only after inspecting KSP's lifecycle constraints.

Pre-implementation scope decision: global native-body registration would make an unsupported torus selectable before P04's admission barrier exists. P03 therefore constructs an inactive native `PSystemBody`/`CelestialBody` prefab and publishes it **only in a detached preview registry**, never `FlightGlobals`/`PSystemManager` or the active saved-world catalog. Its independently owned scaled renderer can be inspected in a human MainMenu preview. Live-system publication and actual map/flight integration move behind P04's admission gate. This revises the proposed publication/lifecycle boundary before coding; it is not a claim of native live-body or map integration.

Acceptance criteria fixed before coding:

1. A strict experimental torus definition validates stable/native identity, dimensions, gravity/reference values, parent/orbit and preview-only capability. It creates coherent closed geometry/material charts and a versioned P02 descriptor. Unsupported or duplicate CFG fields and unsafe dimensions fail explicitly. Render tessellation does not change world identity.
2. A bounded whole-torus scaled mesh has outward analytic normals, consistent winding and watertight periodic topology. Independent tests cover dimensions, solid-distance agreement, shared seams, edge incidence/Euler characteristic, hole preservation, invalid bounds and retessellation. Scaled conversion uses the declared KSP factor and remains separate from body-local metres.
3. Native publication/binding in an owner-scoped registry is single/unique, rejects stable ID/name/index collisions, and constructs isolated inactive native metadata plus a hole-preserving renderer. Real stock/radial body lists, orbit-parent child lists, active world catalog and query ownership remain unchanged. No PQS, vessel collider, forces or flight destination is installed. Native GPU/native triangle-ray comparisons verify hole and surface dimensions; owned mesh/material/texture/camera/frame resources survive repeated create/dispose/unload cycles without leaking.
4. P02 descriptor adoption, exact reload, additive preview catalog and changed torus inputs are exercised in private preview records without adopting the preview into player games. A shipped opt-in human preview and automated launcher expose the tested scaled representation. Native startup and Atlas flight/save/reload regressions pass on exact latest deployed binaries; existing fixture/assets, template assemblies and preexisting save files remain unchanged.
5. Record exact evidence, a native preview capture, human/API guidance and a reflection, then an independent grade. Explicitly distinguish detached prefab/owned preview scenes from live celestial-system, real Map/Tracking/Flight lifecycle and gameplay acceptance. No playable torus or centrifuge credit is awarded.

Rubric: definition/mesh correctness 30; native rendering/lifecycle and reconciliation evidence 30; regression/deployment/preservation 20; API/human documentation 15; scope honesty 5. Target at least 85 with all criteria met and no major defect. Accidental live registration, a selectable unsupported flight destination, discarded saved descriptors or leaked global native resources caps the grade at 59 until repaired.

## P04a — enforced load/start admission (current, development 0.10.0)

Pre-implementation dependency audit split the proposed P04 at its safety boundary. `Game.Load` events follow native FlightState loading. `LoadGameCfg` clears persistent-ID tables before construction, while direct Game and FlightDriver starts have separate entrypoints. First install and verify guards at those entrypoints; live publication/unpack/transfer/terrain consumers then belong to P04b. This split is fixed before coding, rather than claiming a load guard alone certifies arbitrary visits or hole flight.

Policy: permit compatible/additive supported radial records, and unverified legacy radial/native saves with valid references (retain their unverified status). Deny incompatible/future/malformed records, unsupported/detached capabilities, unavailable required catalogs and unknown native vessel references. Re-evaluate mutable inputs; no first-adoption override or migration occurs. New empty native games remain usable. The required HarmonyKSP dependency is pinned and provenance/installation are recorded; Kopernicus remains absent.

Acceptance criteria fixed before coding:

1. A deterministic, bounded core admission policy produces explicit allow/deny reasons. No unknown compatibility/capability or malformed reference is treated as compatible. Legacy permission is explicitly unverified and cannot alter a saved baseline.
2. Version-checked, owner-scoped native prefixes guard LoadGameCfg before construction/ID clearing, Game.Start/Game.Load and both Game/string FlightDriver start routes before their guarded native work. Game-instance checks include current proto references and live/proto scenario records, rather than trusting a stale raw config alone. Install exactly once, preserve foreign patches, detect unsupported patch ownership, and fail startup if required protection cannot be established. Explicitly document entrypoints and bypass limits; this is not an unpack/teleport/active-flight barrier.
3. A native rejection fixture exercises changed geometry/assets/index/provider, missing/preview bodies, future/invalid/duplicate records, bad references and mutable game/proto data. Observe original constructor/ID-clear/FlightState.Load/scene-call work to show rejection occurs before it; snapshots and original saves remain unmodified. Valid/adopted and fresh/legacy states remain admitted. UI supplies a refusal diagnostic without a bypass button.
4. Zero-warning Release build and core tests; native guard suite, Atlas landing/adoption/save/reload and the six historical landed-save plus stock-orbit regression cases pass on exact latest deployed binaries. Runtime dependency files are hash-locked, installed once and never overwrite a different user dependency. Preserve old fixture/assets, template assemblies and existing persistent saves. No live torus is published in this increment.
5. Record exact evidence, hook ordering/ownership/provenance, human/API guidance and reflection, followed by an independent grade. Do not credit P04b hole flight, generic physics, live-body publication or universal save protection to P04a.

Rubric: admission/capability correctness 30; native ordering/rejection evidence 30; regression/deployment/preservation 20; dependency/API/human documentation 15; scope honesty 5. Target at least 85, all criteria met and no unresolved major defect. A tested denied load reaching guarded construction/scene/physics work, silent baseline adoption, bypass through a supported route or unsafe dependency replacement caps the grade at 59 until repaired.

## P05 — first outer-surface contact and saved anchors (proposed)

After admitted hole flight and live publication are safe, bind streamed terrain to real KSP vessels for an airless outer-surface landing, then persist/restore material anchors through save/reload and scene/vessel switches. Benchmark: contact-confirmed landing and restored pose on the actual torus, with multiple nearby participants retaining coverage. Define the exact rails/warp limits before starting; do not infer full static-torus acceptance from one capsule contact.

Inner habitation, EVA/wheels, broader warp and rotating frames require separate acceptance. These are dependency forecasts, not promises that all integration fits a particular number of prompts.
